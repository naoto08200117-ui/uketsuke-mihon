## 1. 考え方：セキュリティは「壁の枚数」で決まる

### 1-1. 多層防御

インフラで言えば「FW → WAF → OSの権限 → アプリの認可」と防御を重ねるのと同じです。どれか1枚が破られても、次の壁で止まるように作ります。

```
        ┌──────────── 攻撃・事故 ────────────┐
        ▼
[壁1] そもそも秘密を置かない・渡さない（運用）
[壁2] Claude Code の権限設定（deny ルール）
[壁3] フック／サンドボックス（OS・プログラムでの強制）
[壁4] アプリのサーバー側での認証・認可・入力チェック
[壁5] DB側の制限（RLS など）・ログと通知・ロールバック
        ▼
   守りたいもの：APIキー、秘密鍵、顧客情報、決済の履歴
```

- 100%防ぐことはできません。分厚い壁を2〜3枚重ねると、費用に対する効果がいちばん高くなります（講座の説明）。
- 「壁を増やそう」という発想を持っていれば、AI にも「その壁を作って」と指示できるようになります。

### 1-2. 「動く」と「公開してよい」は別物

- Claude Code は、動くものをすぐに作れます。しかし作った本人は正しい順番でしか操作しないため、穴があることに気づけません。
- 公開前には必ず**第三者の目**を入れます。他の人に触ってもらうか、AI に攻撃者の視点で点検させるかのどちらかです。

### 1-3. セキュリティは段階で考える

| 段階 | どこまでやるか |
|---|---|
| 練習（ToDoアプリなど、自分のPCだけで動かす） | 第2章（開発環境）だけ徹底する |
| 小さく公開（ユーザー少数・無料） | 第5章のチェックリストのうち「必須」をすべてやる |
| 収益化・ユーザー増加 | 第5章を全部やる。必要なら専門家に診断を依頼する |

セキュリティを気にしすぎて公開できないのも失敗です。ただし**「必須」の項目だけは絶対に省略しない**ことにします。

## 2. 開発環境（Claude Code）のセキュリティ

### 2-1. 穴はどこにあるか

```
あなた ──指示──▶ Claude Code（手を動かす係・あなたのPC上）
                    │  ▲
          「何をすればいい？」  実行結果（ファイルの中身など）
                    ▼  │
               Claude モデル（考える係・Anthropic のサーバー）
```

穴は次の2つです。

1. **危険な操作をしてしまう**：Claude Code は、モデルの判断で `.env` を読む、ファイルを消す、`git push` するといった操作を実行し得ます。
2. **秘密がサーバーに渡る**：Claude Code が読んだファイルの中身はモデルに送られます。APIキーを読ませると、Anthropic 側の記録に残る可能性があります。

> **自分でプロンプトに貼り付けたキーは、どの設定でも防げません。** 本番用のキーは絶対に Claude Code の画面に貼らないでください。

### 2-2. 壁1：秘密の扱い方（運用ルール）

- APIキー・パスワード・トークンは `.env.local` などのファイルに置きます。チャットには貼りません。
- **一度でも漏れた、または AI に読ませたかもしれないキーは、作り直します（ローテーション）。** 作り直せば、古いキーは使えなくなります。
- 開発用（テスト用）のキーと本番用のキーは分けます。公開するときに本番用のキーを新しく発行します。
- `.env*` と `.mcp.json`（APIキーを直接書いている場合）は `.gitignore` に入れ、GitHub に上げません。

### 2-3. 壁2：権限設定（`.claude/settings.json` の deny ルール）

`permissions` には3種類のルールがあります。

- **deny**（禁止）
- **ask**（毎回確認）
- **allow**（自動で許可）

評価は deny → ask → allow の順で、**deny が最優先**です。allow で deny を打ち消すことはできません。

**正しい書き方（公式ドキュメントで確認済み）**

| やりたいこと | 書き方 | 注意 |
|---|---|---|
| どの階層の `.env` 系も読ませない | `"Read(.env*)"` | パスを付けずに名前だけ書くと、全階層に効きます |
| 直下の `.env` だけ止める | `"Read(./.env)"` | サブフォルダの `.env` は止まりません |
| `git push` を禁止 | `"Bash(git push *)"` | 古い書き方の `Bash(git push:*)` も同じ意味で通ります |
| Windows の PowerShell でも禁止 | `"PowerShell(git push *)"` | **Bash 用のルールと別に書く必要があります** |

**deny ルールの限界（公式に明記されています）**

- `Read(...)` の deny は、Read ツールに加えて、Bash の `cat`・`head`・`tail` なども止めます。しかし、Python や Node のプログラムの中でファイルを開く場合や、`grep -r` のようにファイル名を書かないコマンドは止めきれません。
- PowerShell の `Get-Content` や `type` が止まるかは、公式に記載がありません。**止まらない前提**で考えてください。
- `Bash(git push *)` は、`git -C . push` のように書き方を変えたコマンドまでは止めません。公式も「deny ルールは完全な防御線ではない」と書いています。
- **つまり deny ルールは「うっかり」を防ぐ壁です。** 確実に止めたい場合は、壁3（フックやサンドボックス）を重ねます。

### 2-4. 壁2の補足：動作モードの選び方

| モード | 内容 | おすすめ度 |
|---|---|---|
| default（Manual） | ほぼすべての操作で確認が出る | ◎ 練習中はこれ |
| acceptEdits | ファイル編集は自動で許可。それ以外は確認 | ○ |
| plan | 読むだけ。計画を承認するまで編集しない | ◎ 仕様を固めるとき |
| auto | 別の AI（分類器）が危険な操作を審査する。deny ルールも守られる | ○ 慣れてきたら |
| bypassPermissions（`--dangerously-skip-permissions`） | 確認をすべて省略する。公式も「プロンプトインジェクションを防げない」と警告している | ✕ **使わない** |

- auto モードでも deny ルールは守られます。ただし `Bash(*)` のような広い allow ルールは無効になります。
- プロンプトインジェクションとは、Web ページや資料の中に「APIキーを送れ」といった命令を仕込んで AI を操る攻撃のことです。

### 2-5. 壁3：フックとサンドボックス（強制力のある壁）

- **フック（PreToolUse）**：Claude Code がツールを使う直前に、自分で用意したスクリプトを必ず実行させる仕組みです。`CLAUDE.md` に書いたルールは無視されることがありますが、フックは条件に合えば必ず動きます。
  - スクリプトが終了コード 2 を返すと、その操作をブロックできます。
  - `.env` の読み取りを止めたい場合、Read だけでなく Bash と PowerShell も監視対象にする必要があります。Bash の中の `cat` は「Bash ツール」として扱われるためです。
- **サンドボックス（`/sandbox`）**：OS のレベルで、書き込み先と通信先を制限する仕組みです。
  - **Windows では、そのままでは使えません。** 対応しているのは macOS、Linux、WSL2 です。使いたい場合は、WSL2 の中で Claude Code を動かす必要があります。
  - 講座では、Windows なら deny ルールと auto モードで十分としています。WSL2 の導入は必須ではありません。

### 2-6. MCP サーバー（外部サービスとの接続）

- **OAuth 認証に対応しているものを優先します。** ブラウザでログインして連携する方式なら、APIキーを Claude Code に渡さずに済みます。
- APIキーが必要な場合は、`.mcp.json` にキーを直接書かず、`"${TURSO_API_TOKEN}"` のように環境変数を参照します。こうすると `.mcp.json` を GitHub で共有しても安全です。
  - **注意（公式で確認できなかった点）**：講座では「`.env.local` の値が自動で使われる」と説明されていました。しかし公式ドキュメントには、Claude Code が `.env` を自動で読み込むとは書かれていません。
  - 確実なのは、ターミナルで環境変数を設定してから `claude` を起動する方法です。起動後に `claude mcp list` を実行し、警告が出ていないかを確認してください。
- **作者がはっきりしない MCP サーバーは入れません。** マルウェアが仕込まれていた事例があります。
- 本番用のデータベースを MCP でつながないでください。AI が誤ってデータを消すおそれがあります。

### 2-7. 存在しないもの・効かないもの

- **`.claudeignore` は存在しません。** 置いても効果はありません。講座でも後から訂正されています。代わりに Read の deny ルールを使います。
- `CLAUDE_CODE_GLOB_NO_IGNORE` などの設定は、ファイル検索の結果を変えるだけです。読み取りの禁止にはなりません。

### 2-8. GitHub

- リポジトリは**プライベート**で作ります。
- 初回の push の後、GitHub の画面で次の3点を確認します。
  1. プライベートになっていること
  2. `.env*` が上がっていないこと
  3. `.mcp.json` にキーが書かれていないこと
- `.gitignore` に `.env*` を書くと、`.env.local` や `.env.production` などもまとめて除外できます。
- 一度でも GitHub にキーを上げてしまったら、**後でファイルを消しても手遅れです。** 履歴に残るので、キーを作り直してください。

## 3. アプリの守り方（画面・サーバー・DBの3層）

```
[ブラウザ（画面）] ──▶ [サーバー（Next.js の API／Server Actions）] ──▶ [DB]
 誰でも中身を見られる     誰でも直接呼べる（＝公開されたAPI）          キーが漏れたら終わり
```

### 3-1. 画面側（フロントエンド）

- **ブラウザに届いたものは、すべて見られる前提で考えます。** F12 キーで開く開発者ツールで、HTML・JS・通信の中身が誰にでも見えます。
- Next.js では、**`NEXT_PUBLIC_` で始まる環境変数はブラウザ用の JS に埋め込まれます。** 秘密の値に `NEXT_PUBLIC_` を付けてはいけません。
- `'use client'` を書いたファイルと、そのファイルが読み込むものは、すべてブラウザに配信されます。秘密やデータベースへのアクセスは、サーバー側のファイルにだけ書きます。
  - 公式は、サーバー専用のファイルに `import 'server-only'` を書いて守る方法を推奨しています。
  - 実例：Claude Code が Supabase の service role key（何でもできる最強のキー）を `'use client'` のファイルに書き、ブラウザから丸見えになった実演がありました。
- **XSS**（入力欄に悪意のあるスクリプトを書き込む攻撃）は、React や Next.js が標準で防いでくれます。ただし次の2つは例外です。
  - `dangerouslySetInnerHTML` を使うと、その防御が外れます。**原則として使用禁止**にします。
  - ユーザーが入力した URL をリンクに使うときは、`https:` で始まるものだけを許可します。

### 3-2. サーバー側（バックエンド）

- **Server Actions と `route.ts` は、画面を経由しなくても直接呼べます。** Next.js 公式も「公開された HTTP エンドポイントとして扱え」と明記しています。
- **認証と認可は別物です。** マンションに例えると次のとおりです。
  - 認証 ＝ オートロックを通れるか（ログインしているか）
  - 認可 ＝ その部屋の鍵を持っているか（このデータを触ってよい本人か）
  - AI は**認可を書き忘れることが多い**です。
- **IDOR**：URL の ID を1文字変えるだけで、他人のデータが見えてしまう穴です。日報アプリで `/reports/123` を `/reports/124` に変えると他人の日報が見えた、という実演がありました。
- **画面でボタンを隠しただけでは守れません。** 管理者だけが使える削除機能も、サーバー側で「本当に管理者か」を毎回確認します。
- 各処理の先頭で、必ず次の3つを行います。
  1. ログインの確認
  2. 所有者・権限の確認
  3. 入力値の検証
- ページ側でチェックしていても、その中の Server Action までは守られません。
- `middleware`（Next.js 16 では `proxy`）だけで認可するのは危険です。2025年には、特殊なヘッダーを付けるだけで middleware を素通りできる重大な脆弱性（CVE-2025-29927）が見つかりました。**認可は、データに触る処理の中で必ず行います。**
- URL のクエリ（`?isAdmin=true` など）は、利用者が自由に書き換えられます。権限の判定には使いません。
- **レート制限**（1分あたりの回数上限）を入れます。特に AI を呼ぶ処理やメール送信は、連打されると費用やサーバー負荷が跳ね上がります（第4章）。

### 3-3. データベース

- **Supabase** は、画面から直接データベースを操作できる仕組みです。そのため **RLS**（行単位のアクセス制限）の設定が欠かせません。RLS が無効だと、ログインしていない人でもブラウザのコンソールから全件を読めますし、書き込みもできてしまいます。
  - 管理画面で「RLS が無効のテーブル」を一覧で確認できます。
  - AI が SQL で作ったテーブルは、RLS が無効になっていることがあります。
  - service role key は RLS を無視します。原則として使いません。
- **Turso** などのように、必ずサーバーを経由してデータベースに触る構成にすると、サーバー側で認可と検証の壁を挟めます。講座はこちらを推奨しています。
- データベースのトークンが漏れると、データを読まれたり書き換えられたりします。第2章の秘密の扱い方を徹底してください。

### 3-4. 設定ミスと依存パッケージ

- **セキュリティヘッダー**：`next.config` の `headers()` で、全ページに次のヘッダーを付けます。
  - CSP（`frame-ancestors 'none'` を含む）
  - HSTS
  - `X-Content-Type-Options: nosniff`
  - Referrer-Policy
- 本番は `next build` してから動かします。開発モード（`next dev`）のまま公開すると、エラーの全文がブラウザに出てしまいます。
- **パッケージは AI の提案をうのみにしない。**
  - 名前を似せた偽のパッケージ（typosquatting）があります。入れる前に、正式名・週間ダウンロード数・GitHub のリポジトリを確認します。
  - `package-lock.json` はコミットします。
  - `npm audit` で既知の脆弱性を確認します。`npm audit fix --force` は勝手に実行しません。
  - Next.js 本体は、常にセキュリティ修正済みのバージョンに保ちます。

## 4. お金の事故（高額請求）を防ぐ

### 4-1. 実例：放置アプリに約169万円

- 使っていないアプリに、AI が書いた変更の不具合が残っていました。予約の再処理が、**1秒間に約600回**の無限ループで動き続けました。
- そのクラウドは**利用量に応じた課金で、上限で止まる仕組みがありませんでした。** 請求通知は既定の10ドルに設定されたままで、普段の請求額がそれを超えていたため、誰も気にしていませんでした。
- 結果として約2週間気づかず、1万ドルを超える請求になりました。最終的にはサービス側が全額を返金しています。

### 4-2. 対策

| 対策 | 内容 |
|---|---|
| 入力量に上限 | 1回に送れる文字数を制限する（例：300文字）。小説を1冊まるごと貼られても、AI の費用が膨らまないようにする |
| 1人あたりの回数に上限 | 1人が1分または1日に使える回数を制限する |
| 連打・繰り返しを止める | 送信中はボタンを押せないようにする。自動処理には「最低間隔」と「繰り返し回数の上限」を必ず付ける |
| 請求アラート | 想定月額の25%・50%・75%で通知が来るように設定する |
| 上限のないサービスは止め方を先に決める | 自動で止まらないサービスは、自分のシステム側で止める仕組みを作っておく |
| 放置アプリは止めるか消す | 置いてあるかぎり動き続け、課金も続く |
| 自動処理とデータ保存の変更は人間が確認する | AI がこれらを変えたら必ず報告させ、人間が中身を見る |

## 5. 公開前チェックリスト

**必須**は、公開前に1つでも残っていたら公開しません。

| No | 区分 | チェック項目 | 確認方法 |
|---|---|---|---|
| 1 | **必須** | 他人のデータが見えない・操作できない（IDOR・認可） | URL の ID を書き換える。API を直接呼ぶ。AI に攻撃者の視点で点検させる |
| 2 | **必須** | APIキーが画面側に出ていない | `NEXT_PUBLIC_` の値を確認する。ブラウザで「ページのソースを表示」と開発者ツールのネットワークタブを見る |
| 3 | **必須** | 秘密が GitHub に上がっていない | GitHub の画面で `.env*` と `.mcp.json` を確認する。漏れていたらキーを作り直す |
| 4 | **必須** | 権限チェックが画面だけでなくサーバーにもある | 「画面で隠しているだけの操作」を AI に洗い出させる |
| 5 | **必須** | DB の行単位制限（Supabase なら RLS）が全テーブルで有効 | 管理画面で RLS が無効のテーブルを一覧表示する |
| 6 | **必須** | 本番は `next build` で動かす。Next.js が修正済みのバージョン | バージョンを確認する。`npm audit` |
| 7 | 推奨 | 費用の上限とアラート（入力量・回数・繰り返し・請求通知） | 第4章 |
| 8 | 推奨 | 想定外の操作で壊れない | 0件、極端に長い文字、絵文字、日付と時差（日本時間）、送信後の「戻る」による二重送信。**他の人に説明なしで触ってもらう** |
| 9 | 推奨 | 入力値の検証、`dangerouslySetInnerHTML` を使っていない | AI に点検させる |
| 10 | 推奨 | セキュリティヘッダー | 開発者ツールのネットワークタブでヘッダーを確認する |
| 11 | 推奨 | 気づける・戻せる | エラーが記録に残るか（個人情報やキーは記録しない）。自分に通知が来るか。1つ前のデプロイに戻せるか。DB の構造変更を戻す手順があるか |

## 6. Claude Code に渡す指示文の型

必要な場面でコピペして使ってください。【 】の部分を書き換えます。

**攻撃者の視点で点検させる（IDOR・認可）**
```
あなたは攻撃者です。このアプリで「他人のデータを見る・変更する・削除する」方法を探してください。
URLのIDを書き換える場合と、API（Server Action・route.ts）を画面を通さず直接呼ぶ場合の両方を試す前提で、
認可チェック（データの持ち主かどうかの確認）が抜けている箇所を、ファイル名と行番号つきで一覧にしてください。
まだ修正はしないでください。
```

**秘密の露出を点検させる**
```
ブラウザに配信されるコード（'use client' のファイル、NEXT_PUBLIC_ の環境変数、その import 先）と、
サーバーだけで動くコードを分けて一覧にしてください。
ブラウザ側に、APIキー・トークン・秘密の値が含まれていないかを確認し、結果を報告してください。
.env 系のファイルの中身は読まないでください（変数名だけで判断すること）。
```

**画面で隠しているだけの権限を洗い出させる**
```
画面で表示・非表示を切り替えているだけで、サーバー側で権限を確認していない操作をすべて洗い出してください。
各操作について「誰が実行できるべきか」と「今サーバーで確認しているか」を表にしてください。
```

**費用の暴走を点検させる**
```
有料の外部API（AIなど）を呼んでいる処理と、自動で繰り返し実行される処理をすべて挙げてください。
それぞれについて「1回の入力量の上限」「1人あたりの回数制限」「繰り返しの最低間隔と回数の上限」があるかを表にしてください。
```

**気づける・戻せるかを点検させる**
```
エラーが起きたときに、①記録が残るか（個人情報やキーを含めずに）、②私に通知が来るか、③直前の状態に戻せるか、を確認して報告してください。
データベースの構造を変更した場合の戻し方も説明してください。
```

## 付録A：講座の説明と公式ドキュメントの食い違い

| 講座での説明 | 公式ドキュメントでの事実 | このガイドでの扱い |
|---|---|---|
| `.claudeignore` で読ませないようにできる | 存在しない（講座でも後から訂正） | 使わない。Read の deny ルールを使う |
| `"Read(.env*)"` で .env を拒否できる | 正しい。名前だけのパターンは全階層に効く | このまま採用する |
| `.mcp.json` の `${VAR}` は `.env.local` の値を使う | 公式には `.env` を自動で読むとは書かれていない | 環境変数を設定してから起動し、`claude mcp list` で確認する |
| deny を設定すれば `.env` は読まれない | Read の deny は Bash の `cat` などにも効くが、PowerShell やプログラム経由の読み取りまでは保証されない | フックを重ねる（多層防御） |
| Windows でもサンドボックスを使える（WSL が必要） | ネイティブの Windows は非対応。WSL2 の中で動かせば使える | 一致している。導入は任意 |
| auto モードでは allow が設定されない | 狭い allow は有効。広い allow（`Bash(*)` など）だけが無効になる | 正確な説明に差し替え |

## 付録B：用語集

| 用語 | ひとことで |
|---|---|
| 認証 | ログインしている本人かの確認（オートロック） |
| 認可 | その操作をしてよい人かの確認（部屋の鍵） |
| IDOR | ID を書き換えるだけで他人のデータに触れてしまう穴 |
| XSS | 入力欄からスクリプトを仕込む攻撃 |
| CSRF | 他サイトから勝手に送信させる攻撃（Server Actions は標準で対策あり） |
| RLS | DB の行単位のアクセス制限（Supabase で必須） |
| レート制限 | 一定時間あたりの回数の上限 |
| ローテーション | キーを作り直して、古いキーを無効にすること |
| プロンプトインジェクション | 資料や Web ページに AI への命令を仕込む攻撃 |
| 多層防御 | 壁を何枚も重ねる考え方 |
