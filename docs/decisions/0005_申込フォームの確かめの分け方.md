# 申込フォームの確かめを「入力の形」と「読み直したデータでの確かめ」に分け、エラーを付ける欄を決めた

## 決めたこと

- **入力の形**（名前→連絡先→メールの形→電話の形→希望日）は `src/lib/reservationValidate.ts` の `checkApplyInput` で確かめる。前後の空白を除き、電話を半角に直した値を返す（保存するのはこの値）
- **残り席（F-16）→ 同じ連絡先・同じ日（F-17）→ 300件（F-18）** は、`src/app/page.tsx` の `submit` から `updateReservations` に渡す変更の関数の中で、**保存の直前に読み直したデータ**で確かめる。当たったら `null` を返して書かない
- F-17 の比べ方は `sameContactField`（メールは小文字、電話は数字だけ。空の欄どうしは比べない）。当たった欄（メールか電話）を返す
- `crypto.randomUUID()` と `new Date().toISOString()` は `submit`（「申し込む」を押した時）の中だけで呼ぶ
- エラーを付ける欄（`aria-invalid="true"`・`aria-describedby="apply-error"`・フォーカス）：
  - F-10 → お名前／F-12・F-13 → メールアドレス（F-12 は要件定義書 F3 のとおり）／F-14 → 電話番号／F-15 → 希望日
  - **F-16 → 人数**（確かめが「人数 ＞ 残り」のため）
  - **F-17 → 当たった欄**（メールが同じならメール、電話が同じなら電話）
  - **F-18 → 付ける欄がないので、どの欄にも `aria-invalid` を付けず、メッセージの要素（`tabIndex=-1`）にフォーカスを移す**
- メールの欄は `type="text"`（`inputMode="email"`）。`type="email"` は Chrome が値を直す（前後の空白を除く・全角のドメインを変換する）ことがあり、「全角は直さず、形の誤り」（F2）にならないおそれがあるため
- 「申し込む」の2回押しは、`useRef` の印で描き直しを待たずに止め、`disabled` も付ける。成功したらフォームが完了の表示に入れ替わるので、`disabled` は戻さない

## 背景（なぜ決める必要があったか）

- 要件定義書 F3 は、残り席・F-17・F-18 を読み直したデータで確かめるよう決めている（別のタブで申し込まれた分を数えるため）
- F-16・F-17・F-18 は、どの欄にエラーを付けるかが要件定義書に書かれていなかった

## 検討した他の案と、選ばなかった理由

- すべての確かめを画面が持っているデータで行う：別のタブの申込を見落とし、定員を超えるおそれがある
- F-16 を希望日の欄に付ける：日を変えても人数を減らしてもよいが、確かめの式が「人数 ＞ 残り」なので人数にした
- F-18 を「申し込む」ボタンに付ける：ボタンに `aria-invalid` は意味がなく、ボタンにフォーカスしても文言が読まれにくい
- 新しいファイル（例：`lib/applyForm.ts`）を作る：CLAUDE.md のファイル構成にないため、既にある `reservationValidate.ts` と `page.tsx` に分けて入れた

## この決定による影響・注意点

- `reservationValidate.ts` は131行になった。`ApplyForm.tsx` も123行（「おおむね100行」を少し超える）。分けるなら新しいファイルが要るので、nao さんの判断を待つ
- 名前の30字・ご要望の200字・メールの100字は入力欄の `maxLength` で止めている（この長さを超えたときの文言は11章にない）
