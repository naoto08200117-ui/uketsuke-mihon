# 管理一覧は「進める計算」を status.ts に置き、表とスマホの枠で同じ小さな部品を使う形にした

## 決めたこと

- 「次の操作」の計算（読み直したデータで、id の申込を、押した時に見えていた状態の次にする）は `src/lib/status.ts` の `advanceStatus` に置いた。申込がない・状態が違う・次がないときは `null` を返し、`updateReservations` は書かずに描き直すだけにする（[[0004_保存と読み直しの設計]]）。T05 の詳細の「次の操作」も同じ関数を使える
- `NextStatusButton` は `event.detail >= 2` を無視する。文言 A-09 は、`updateReservations` の結果が `"unchanged"` でないとき（保存できた・メモリに持った）だけ出す。`"unchanged"` のときは前の文言をそのまま残す（T04⑥ の「前の『確定にしました』は出たままでよい」）
- A-09・A-11 は、S-01〜S-04 と同じ `MessageArea`（`role="status"`）に、S-0x の下に1つだけ出す（最後に出したもの）
- PC の表（`ReservationTable`）とスマホの枠（`ReservationCards`）の両方を描き、CSS（`md:table`・`md:hidden`）で片方だけを見せる。名前（キャンセルは取り消し線）・連絡先・詳細のリンクは `ReservationTable.tsx` から書き出して、両方で使う
- 2つ目のボタンのクラスは `src/components/form/Field.tsx` の `secondaryButtonClass` にまとめ、T03 の `ApplyDone` もこれを使うようにした（見た目は同じ。押せないときの見た目を足した）
- 絞り込みのボタンは、選んでいるときだけ `border-accent text-accent`、選んでいないときは `border-line text-ink` を付ける（両方を付けると、どちらが効くかがクラスの順で決まらないため）
- 並べ替えは `localeCompare` を使わず、文字の大小で比べる（`Intl` の並べ方を使わない決まりのため。日付・日時は桁のそろった形なので、文字の順＝日時の順）
- 「架空のデータに戻す」の確認（A-10）を出したら「やめる」にフォーカスを移し、閉じたら元のボタンに戻す（キーボードで操作したときに迷わないように。消さない方を先に選ばせる）
- 絞り込みの件数は、検索に関係なく全件で数える

## 背景（なぜ決める必要があったか）

- 要件定義書に、A-09 を出す場所、件数の数え方（検索と絞り込みの関係）、確認を出したときのフォーカスが書かれていなかった
- 表とスマホの枠で同じ表示を2回書くと、片方だけ直し忘れるおそれがある

## 検討した他の案と、選ばなかった理由

- 画面の幅を JavaScript で見て、表か枠のどちらか1つだけを描く：書き出しの時（サーバー側）は幅が分からず、Hydration のずれの元になる
- 共通の部品を新しいファイルにする：CLAUDE.md のファイル構成にないファイルを作ることになるため、既にある `ReservationTable.tsx` と `Field.tsx` に入れた
- A-09 を各行の横に出す：11章に場所の決まりがなく、文言の場所が増えると読み上げが分かりにくい

## この決定による影響・注意点

- 表と枠の両方に同じボタンがあるが、見えていない方（`display: none`）は Tab で止まらず、クリックもできない
- メッセージの欄は danger の色（DESIGN.md「メッセージ」）なので、A-09・A-11 も danger で出る。色を変えたいときは DESIGN.md への追記が要る
