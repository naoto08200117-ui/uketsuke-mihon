# 詳細の画面は、状態を変える計算を status.ts にそろえ、メモは保存したデータをそのまま入力欄に出す形にした

## 決めたこと

- 「キャンセルにする」「1つ前に戻す」の計算は、T04 の `advanceStatus` と同じ形で `src/lib/status.ts` に `cancelStatus`・`undoStatus` として置いた。3つとも、押した時に見えていた状態（ボタンの元の状態）を受け取り、読み直したデータで状態が違う・押せない形なら `null` を返す（書かずに描き直すだけ）。共通の部分は `changeStatus`・`findShown`（ファイルの中だけの関数）にまとめた
- `undoStatus` は、キャンセルから戻すときに読み直したデータの残り席が人数より少なければ `"noSeats"` を返す。画面はそのとき R-07 を出し、何も書かない
- 「次の操作」は管理一覧の `NextStatusButton` をそのまま使う。詳細では、次がない（完了・キャンセル）ときはボタンも「—」も出さない（ラフ図に「—」がないため）
- 状態を変えたときの文言は、3つのボタンとも A-09「「{名前}」を{状態}にしました。」（ink）。R-07 はエラーなので danger。どちらも最後に出したもの1つだけ（[[0006_管理一覧の部品の分け方]] と同じ）
- メモの入力欄は、保存したデータ（`useReservations`）の `memo` をそのまま値にする。入力のたびに `updateReservations` で、読み直したデータのその申込のメモだけを変える。別の画面用の値を `useState` で持たない
- 詳細の id は、`isValidId`（`^[A-Za-z0-9-]{1,64}$`。読み込みの検証と同じ関数）を通してから探す。通らない・見つからないときは R-05（danger）
- `useSearchParams` を使う部分だけを `<Suspense>` で囲み、見出しと「管理一覧に戻る」は外に置いた（書き出しの HTML にも見出しが入る）
- 日時の表示は `dateFormat.ts` の `formatDateTime`（UTC に9時間足して `getUTC*` で読む）

## 背景（なぜ決める必要があったか）

- 要件定義書に、詳細で「キャンセルにする」「1つ前に戻す」の後に出す文言と、完了・キャンセルのときの「次の操作」の見せ方が書かれていなかった
- メモを画面の中だけの値で持つと、別のタブで変えたメモが見えず、保存した値と画面がずれる

## 検討した他の案と、選ばなかった理由

- キャンセル・戻すの計算を部品の中に書く：一覧の「次の操作」と決まりがずれるおそれがある
- メモを `useState` で持ち、少し待ってから保存する：要件は「入力のたびに保存」。待つ間に F5 すると消える
- 戻した後に文言を出さない：押した結果が分かりにくい。A-09 は「状態を変えた」の文言なので使える

## この決定による影響・注意点

- `status.ts` は `seats.ts` を読み込むようになった（残り席の確かめのため。逆向きの読み込みはない）
- メモを打つたびに localStorage を読み直して検証する（300件で約300KB）。今の件数の上限なら問題ないと見ている
